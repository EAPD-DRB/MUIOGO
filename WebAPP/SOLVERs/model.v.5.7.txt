# model.v.5.8 CANDIDATE (2026-08-13) - matrix de-bloat / density reduction.
# Derived from model.v.5.7 (as installed with MUIO). All changes are exact
# reformulations of the same LP - the optimal objective is unchanged -
# except items (4)/(5), which enforce a data policy with hard compile-time
# checks. Summary of changes (search for "v5.8:" tags):
#  1. Aggregate substitution: annual-level activity terms reference
#     TotalAnnualTechnologyActivityByMode (defined by Acc3_TS/Acc3_S)
#     instead of inline sums over TIMESLICE/SEASON. Applied in
#     EB_AnnualBalance, AAC1_TS, AAC1_S, CAb1_TS, CAb1_S and the objective
#     (whose TS block collapses into the S/AN block - one block for all
#     technologies). Exact because Input/OutputActivityRatio and
#     VariableCost carry no timeslice index.
#  2. Capacity single point of truth: constraints and objective reference
#     TotalCapacityAnnual / AccumulatedNewCapacity (CAa1/CAa2) instead of
#     re-expanding sum{yy} NewCapacity inline. Storage SC1-SC4 likewise use
#     AccumulatedNewStorageCapacity (SI3).
#  3. Row/column hygiene: S30 no longer duplicates one row per timeslice;
#     CAa3 + RateOfTotalActivity exist only for profiled technologies
#     (they serve only OP1); Trade variables and EBa10 symmetry rows exist
#     only where a TradeRoute is nonzero.
#  4. EB_TimesliceAnnualBalance and EBb4_EnergyBalanceEachYear4_ICR are
#     removed: for commodities without AccumulatedAnnualDemand/InputTo*
#     they duplicate the per-resolution balances row-for-row (pure bloat,
#     and parallel duplicate rows split the commodity's dual price
#     arbitrarily). Their one real job - carrying AAD/InputTo* for
#     non-ANNUAL commodities - moves to EB_AnnualRollup, generated ONLY
#     for the commodities that actually need it (in cheap aggregate form),
#     so legacy models imported with everything at TIMESLICE level keep
#     working unchanged. A printf NOTE lists each such commodity and
#     suggests reclassifying it to ANNUAL, which removes the extra row
#     and gives a clean single dual price.
#  5. Legacy datafile compatibility: COMMODITY_TS/S/AN carry defaults -
#     a datafile that never declares them (pre-balance-level MUIO export)
#     compiles with every commodity at TIMESLICE, matching MUIO's import
#     convention. Datafiles that declare the sets are unaffected.
#  6. E2/E5/E8/E9 and the emission variables are generated only for
#     (technology, emission) pairs that actually have an
#     EmissionActivityRatio or EmissionToActivityChangeRatio link
#     (set TECHNOLOGYxEMISSION), instead of all combinations.
#  7. "Unlimited = -1" on the six UPPER limits: enter -1 for
#     TotalTechnologyAnnualActivityUpperLimit (AAC2),
#     TotalTechnologyModelPeriodActivityUpperLimit (TAC2),
#     TotalAnnualMaxCapacityInvestment (NCC1), TotalAnnualMaxCapacity
#     (TCC1), AnnualEmissionLimit (E8) or ModelPeriodEmissionLimit (E9)
#     and the constraint is not generated at all - no row, and no bound
#     for the solver to park a cost-indifferent variable on. This
#     replaces the convention of typing a large placeholder (999999),
#     which is a real constraint: it keeps a row per technology-year in
#     the matrix, and zero-cost technologies settle exactly on it, so
#     the results show a capacity of 999999 that means "unconstrained".
#     0 cannot serve as the off switch here the way it does for the
#     LOWER limits (AAC3/TAC3/NCC2/TCC2) and the by-mode limits
#     (LU1/LU3/LU4), because on an upper limit 0 legitimately means
#     "this may not run". BACKWARDS COMPATIBLE: any other value,
#     999999 included, still generates the constraint exactly as before,
#     so existing datafiles are unaffected.
# NOTE: written for GLPK MathProg (glpsol), which MUIO uses. Some
# constructs (setof, exists, membership conditions) are NOT supported by
# the mosox compiler; a mosox port would need the pair-set patterns from
# the v7 research model.
#

# Technology balance level - derived from commodity balance levels, PLUS
# storage linkage (see STORAGE FIX note below).
# Checks both input and output commodities; highest resolution wins.
# COMMODITY_TS/S must be defined before this parameter.
#
# STORAGE FIX (model.v.5.7.Storage.txt only): a technology that charges or
# discharges any storage (TechnologyToStorage/TechnologyFromStorage > 0) is
# always forced to TIMESLICE, regardless of the balance level of the
# commodities it consumes/produces. This does NOT change how those
# commodities themselves are balanced (COMMODITY_TS/S/AN membership is
# untouched, and the energy-balance equations still aggregate a TIMESLICE
# technology's contribution up to the commodity's own Season/Annual level via
# YearSplit, exactly like the existing "irrigation pump" case below). It only
# ensures the technology's own activity is tracked finely enough for storage
# charge/discharge to be computable at all - RateOfActivity is only defined
# for TECHNOLOGY_TS, and storage level tracking is inherently sub-annual.
# Without this, a storage-linked technology whose commodities are all
# Season/Annual would end up in TECHNOLOGY_S/TECHNOLOGY_AN and the storage
# equations (S9/S10, S11/S12 below) would reference an undefined
# RateOfActivity index, crashing the solve.
param TechnologyBalanceLevel{t in TECHNOLOGY} symbolic :=
    if (exists{f in COMMODITY_TS, (m,tt) in MODExTECHNOLOGYperFUELout[f]: tt=t} 1=1)
    or (exists{f in COMMODITY_TS, (m,tt) in MODExTECHNOLOGYperFUELin[f]:  tt=t} 1=1)
    or (exists{r in REGION, s in STORAGE, m in MODE_OF_OPERATION: TechnologyToStorage[r,t,s,m] > 0} 1=1)
    or (exists{r in REGION, s in STORAGE, m in MODE_OF_OPERATION: TechnologyFromStorage[r,t,s,m] > 0} 1=1)
    then "TIMESLICE"
    else if (exists{f in COMMODITY_S, (m,tt) in MODExTECHNOLOGYperFUELout[f]: tt=t} 1=1)
         or (exists{f in COMMODITY_S, (m,tt) in MODExTECHNOLOGYperFUELin[f]:  tt=t} 1=1)
    then "SEASONAL"
    else "ANNUAL";

# Derived technology subsets by balance level.
# A technology is assigned the highest resolution of any commodity it touches
# (input or output), OR TIMESLICE if it is linked to storage (see STORAGE FIX
# above). TIMESLICE takes precedence over SEASONAL over ANNUAL.
# Example: an irrigation pump taking electricity (TIMESLICE) and outputting
# water (SEASONAL) is assigned TIMESLICE so its electricity draw is
# disaggregated correctly.
set TECHNOLOGY_TS := {t in TECHNOLOGY: TechnologyBalanceLevel[t] = "TIMESLICE"};
set TECHNOLOGY_S  := {t in TECHNOLOGY: TechnologyBalanceLevel[t] = "SEASONAL"};
set TECHNOLOGY_AN := {t in TECHNOLOGY: TechnologyBalanceLevel[t] = "ANNUAL"};

# v5.8: non-ANNUAL commodities that carry annual-quantity data
# (AccumulatedAnnualDemand or capacity-input relationships). For exactly
# these commodities an annual roll-up balance (EB_AnnualRollup below) is
# generated so that data is honoured - this preserves the behaviour of
# models imported from MUIO versions without balance levels, where every
# commodity sits at TIMESLICE level. In a fully classified model this set
# is EMPTY and no roll-up rows exist. Prefer reclassifying these
# commodities to ANNUAL: the roll-up row parallels the commodity's own
# balance, and parallel rows split the commodity's dual price (marginal
# cost) arbitrarily between them.
set COMMODITY_ANNUAL_ROLLUP :=
    {f in COMMODITY diff COMMODITY_AN:
        (exists{r in REGION, y in YEAR} AccumulatedAnnualDemand[r,f,y] <> 0)
        or (exists{(t,ff) in INPUT_TF_PAIRS_NEW} ff = f)
        or (exists{(t,ff) in INPUT_TF_PAIRS_TOTAL} ff = f)};

# OperationalProfile fixes the share of total annual activity occurring in
# each timeslice. Optional: technologies with no entries (all defaults, i.e.
# zero in every timeslice) are unconstrained - existing behaviour.
# The shares are normalised by their sum across timeslices, so they need not
# sum to exactly 1 (a warning is printed if they deviate by more than 1%).
# The constraint binds activity to the profile shape but not its level, so a
# profiled technology with capacity can still choose not to operate at all.
# Only applies to TECHNOLOGY_TS - profiles on seasonal or annual resolution
# technologies are ignored (a warning is printed).
param OperationalProfile{r in REGION, t in TECHNOLOGY, l in TIMESLICE, y in YEAR} >= 0;

# Data validation (warning only): profile shares are normalised to sum to 1
# in OP1_TS_OperationalProfile, so a profile that does not sum to 1 is still
# usable - only its shape matters. A sizeable deviation (>1%) usually points to
# a data error (e.g. a missing timeslice), so flag it in the solver log.
printf{r in REGION, t in TECHNOLOGY, y in YEAR:
       sum{l in TIMESLICE} OperationalProfile[r,t,l,y] > 0
       and abs(sum{l in TIMESLICE} OperationalProfile[r,t,l,y] - 1) > 0.01}
    "WARNING: OperationalProfile for %s/%s/%s sums to %.4f (not 1); shares will be normalised\n",
    r, t, y, sum{l in TIMESLICE} OperationalProfile[r,t,l,y];

# Data validation (warning only): OP1_TS_OperationalProfile is indexed over
# TECHNOLOGY_TS, so a profile on a seasonal or annual resolution technology is
# silently ignored. Flag it so the modeller knows the data has no effect.
printf{r in REGION, t in TECHNOLOGY, y in YEAR: t not in TECHNOLOGY_TS
       and sum{l in TIMESLICE} OperationalProfile[r,t,l,y] > 0}
    "WARNING: OperationalProfile for %s/%s/%s is ignored - technology is not at TIMESLICE resolution\n",
    r, t, y;

# The objective is expressed in terms of named cost variables for clarity.
# Each term is defined by a corresponding constraint below.
#
# v5.8: single resolution-agnostic block for ALL technologies. The former
# TIMESLICE block inlined RateOfActivity over every timeslice, making the
# objective by far the densest row of the matrix; via the Acc3_TS aggregate
# it is identical in form to the S/AN block, so the two blocks merge.
# Fixed cost references AccumulatedNewCapacity (CAa1) instead of
# re-expanding the NewCapacity sum - one nonzero per (t,y). NOTE: kept as
# AccumulatedNewCapacity + ResidualCapacity (NOT TotalCapacityAnnual) so
# the ResidualCapacity*FixedCost part stays a CONSTANT, exactly as in
# v5.7 - MPS files cannot carry objective constants, so a solver run from
# an MPS (as MUIO does with CBC) drops it; putting it on a variable would
# shift every reported objective by the residual fixed-O&M present value.
minimize cost:
    sum{r in REGION, t in TECHNOLOGY, y in YEAR} (
        (
            (AccumulatedNewCapacity[r,t,y] + ResidualCapacity[r,t,y])
            * FixedCost[r,t,y]
            + sum{m in MODEperTECHNOLOGY[t]}
                TotalAnnualTechnologyActivityByMode[r,t,m,y] * VariableCost[r,t,m,y]
        ) / ((1+DiscountRate[r])^(y-min{yy in YEAR} min(yy)+0.5))
        + CapitalCost[r,t,y] * NewCapacity[r,t,y]
          * CapitalRecoveryFactor[r,t] * PvAnnuity[r,t]
          / ((1+DiscountRate[r])^(y-min{yy in YEAR} min(yy)))
        + sum{e in EMISSION} (
            sum{(m,tt) in MODExTECHNOLOGYperEMISSION[e]: t=tt}
                EmissionActivityRatio[r,t,e,m,y]
                * TotalAnnualTechnologyActivityByMode[r,t,m,y]
            + sum{(m,tt) in MODExTECHNOLOGYperEMISSIONChange[e]: t=tt}
                EmissionByActivityChange[r,t,e,m,y]
          ) * EmissionsPenalty[r,e,y]
          / ((1+DiscountRate[r])^(y-min{yy in YEAR} min(yy)+0.5))
        - DiscountedSalvageValue[r,t,y]
    )
    + sum{r in REGION, s in STORAGE, y in YEAR} (
        CapitalCostStorage[r,s,y] * NewStorageCapacity[r,s,y]
        / ((1+DiscountRate[r])^(y-min{yy in YEAR} min(yy)))
        - DiscountedSalvageValueStorage[r,s,y]
    );

##########  Operational profiles  ##########

# OP1_TS: For profiled timeslice technologies, activity in each timeslice
# equals the profile share of total annual activity.
# Generated for ALL timeslices of a profiled (r,t,y) - including those with a
# zero share, which forces zero activity there (otherwise the model could
# relocate activity into unlisted timeslices).
# The constraint is homogeneous in activity: if TotalTechnologyAnnualActivity
# is zero it is trivially satisfied, so no operation is ever forced and idle
# capacity remains possible.
s.t. OP1_TS_OperationalProfile
    {r in REGION, t in TECHNOLOGY_TS, l in TIMESLICE, y in YEAR:
     sum{ll in TIMESLICE} OperationalProfile[r,t,ll,y] > 0}:
    RateOfTotalActivity[r,t,l,y] * YearSplit[l,y]
    = (OperationalProfile[r,t,l,y]
       / sum{ll in TIMESLICE} OperationalProfile[r,t,ll,y])
      * TotalTechnologyAnnualActivity[r,t,y];

##########  Salvage value constraints  ##########

s.t. SV1_SalvageValueAtEndOfPeriod1
    {r in REGION, t in TECHNOLOGY, y in YEAR:
     (y + OperationalLife[r,t]-1) > (max{yy in YEAR} max(yy)) && DiscountRate[r] > 0}:
    SalvageValue[r,t,y]
    = CapitalCost[r,t,y] * NewCapacity[r,t,y]
      * CapitalRecoveryFactor[r,t] * PvAnnuity[r,t]
      * (1-(((1+DiscountRate[r])^(max{yy in YEAR} max(yy) - y+1)-1)
            /((1+DiscountRate[r])^OperationalLife[r,t]-1)));

s.t. SV2_SalvageValueAtEndOfPeriod2
    {r in REGION, t in TECHNOLOGY, y in YEAR:
     (y + OperationalLife[r,t]-1) > (max{yy in YEAR} max(yy)) && DiscountRate[r] = 0}:
    SalvageValue[r,t,y]
    = CapitalCost[r,t,y] * NewCapacity[r,t,y]
      * CapitalRecoveryFactor[r,t] * PvAnnuity[r,t]
      * (1-(max{yy in YEAR} max(yy) - y+1)/OperationalLife[r,t]);
